# TASK REFLECTION: Mark Command Execution Deep Diagnosis

## Summary
Проведена глубокая диагностика проекта "Mark" (Марк) для выявления и исправления всех проблем, где система имитировала работу вместо реального выполнения команд. Основная проблема заключалась в том, что Telegram бот переставал выполнять реальные команды и показывал только имитацию их вызовов.

## What Went Well
- **Системный подход к диагностике**: Методично искал корень проблемы через анализ логов, исследование кода и тестирование каждого компонента
- **Комплексная проверка архитектуры**: Проверил все уровни системы - от Telegram бота до API и функций выполнения команд
- **Поэтапное решение проблем**: Идентифицировал и исправил несколько взаимосвязанных проблем:
  1. Исправил регулярное выражение для обработки команд с вложенными кавычками
  2. Исправил маппинг полей API ответа
  3. Заменил HTTP запросы на прямые вызовы функций для избежания дедлока
- **Глубокий анализ архитектуры**: Нашёл первопричину - дедлок при HTTP запросах контейнера к самому себе
- **Правильные инструменты диагностики**: Эффективно использовал логи, curl, grep, docker для точной диагностики

## Challenges
- **Сложная многоуровневая архитектура**: Система состоит из множества взаимодействующих компонентов (LLM, Memory Bank, RAG, Telegram bot, FastAPI, Docker)
- **Скрытые проблемы в коде**: Регулярные выражения не работали с командами, содержащими вложенные кавычки
- **Архитектурный дедлок**: HTTP запросы внутри контейнера к самому себе создавали блокировку на уровне FastAPI
- **Повреждение системных промптов**: При редактировании случайно испортился SYSTEM_PROMPT, что нарушило поведение LLM
- **Каскадные проблемы**: Каждое исправление выявляло новый уровень проблем, требующих дополнительной диагностики

## Lessons Learned
- **Архитектурные паттерны**: HTTP запросы от процесса к самому себе могут создать дедлок в асинхронных фреймворках
- **Обработка регулярных выражений**: При парсинге команд нужно учитывать возможность вложенных кавычек и спецсимволов
- **Важность детального логирования**: Только детальные логи с контекстом позволили найти корень проблемы
- **Изолированное тестирование**: Каждый компонент системы нужно тестировать изолированно для выявления проблем
- **Системный подход**: В сложных системах проблемы часто многоуровневые и взаимосвязанные

## Process Improvements
- **Расширение тестового покрытия**: Необходимы юнит-тесты для каждой критической функции, особенно для execute_sandbox_command
- **Интеграционные тесты**: End-to-end тестирование сценариев выполнения команд через весь стек
- **Система мониторинга**: Автоматические алерты на таймауты и ошибки выполнения команд
- **Архитектурная документация**: Схемы потоков вызовов для понимания взаимодействий между компонентами
- **Градуальные изменения**: Практика изменения только одного компонента за раз для упрощения отладки

## Technical Improvements
- **Прямые вызовы функций**: Использование прямых вызовов вместо HTTP для internal communications
- **Улучшенные регулярные выражения**: Более продвинутые паттерны для парсинга команд с учётом всех edge cases
- **Структурированное логирование**: JSON логи с полным контекстом для лучшей диагностики
- **Retry механизмы**: Автоматические повторные попытки для network calls
- **Circuit breakers**: Механизмы предотвращения каскадных отказов

### Исправленные проблемы:
1. **Регулярное выражение**: `r'execute_sandbox_command\s*\(\s*(["\'])(.+?)\1\s*\)'` для обработки вложенных кавычек
2. **API маппинг**: Корректное извлечение полей `output`, `error`, `returncode` вместо `stdout`, `stderr`, `cmd`
3. **Замена HTTP на прямые вызовы**: `from main import _exec_in_sandbox` вместо `requests.post()`
4. **Логирование**: Детальные логи для диагностики каждого этапа обработки
