# Самообновление с восстановлением

В версии 2.4 Марк может исследовать свой код, проверить кандидат через
`self.experiment` и запросить установку через `self.request_upgrade`.
Это обучение программы на проверенных изменениях, а не изменение весов модели.
Обычный `scripts/start.sh` оставляет режим экспериментов без установки.

## Как пользоваться

Напиши конкретную задачу: «Улучши поиск в памяти: сейчас запрос … пропускает …;
добавь проверку этого случая и установи исправление, если проверки проходят».
Можно использовать `/evolve <задача>`. Марк сохраняет исходный код, патч,
проверки и результаты обеих версий. Запрос установки привязан к исходному
поручению владельца. Расписание и импортированная переписка такого права не дают.

`self.upgrade_status` показывает состояние независимого guardian: проверка,
ожидание завершения текущей работы, установка, наблюдение, принятие или откат.
Успешный эксперимент и отправленный запрос ещё не означают установленную версию.

В личном чате владельца работают аварийные команды:

- `/rollback` — вернуть предыдущую рабочую версию, сохранив совместимую целую базу.
- `/rescue` — вернуть рабочую версию и защищённую контрольную копию базы.
  Текущая база сначала сохраняется отдельно для разбора.

Эти команды принимает bridge, даже если основной бот не запускается. Входящие
сообщения записаны в его независимый журнал и доступны после восстановления.
Незавершённые задачи и отправки с неизвестным результатом блокируются для
проверки; повтор по сети нельзя безусловно считать безопасным. `/resume` и
`/extend` — явное решение владельца продолжить работу, а не сброс бюджета.

## Почему Марк не может удалить своё восстановление

Защищённая установка состоит из трёх отдельных процессов:

1. Основной бот получает свою память, рабочие файлы, runner и узкий сокет bridge.
   Он может менять до трёх Python-модулей за один кандидат. Зависимости, образы,
   Dockerfile, конфигурация хоста и сам guardian не входят в запрос обновления.
2. Закреплённый bridge хранит Telegram-токен, отдельный OpenAI API-ключ для речи,
   существующий официальный каталог Codex и журнал сетевых результатов.
   Каталог авторизации монтируется на прежнем месте; OAuth-файлы не копируются.
3. Root-owned guardian вне контейнера проверяет и устанавливает код. Его образы,
   журнал переходов и контрольные копии недоступны боту. Проверки кандидата
   выполняются без сети и секретов. После установки guardian наблюдает процесс,
   heartbeat, историю и схему базы, а не только ответ «готов» от кандидата.

При ошибке основной процесс можно заменить, даже когда Python-код бота больше
не импортируется. Старые образы и проверенная первоначальная версия сохраняются.
Восстановление ограничено числом попыток, чтобы неисправность не вызывала
бесконечную перезагрузку. При исчерпании попыток bridge остаётся отдельным
процессом, а guardian сообщает `manual_intervention`.

## Обслуживание защищённой установки

Установленные пути: `/opt/marka-guardian/guardian.py`,
`/etc/marka-guardian/config.json`, `/var/lib/marka-guardian/`.
Это приватные данные хоста, они не должны попадать в Git или в mounts бота.
Сервис: `deploy/marka-guardian.service`. Контракт настройки и протоколов:
[SELF_UPGRADES_DESIGN.md](SELF_UPGRADES_DESIGN.md).

```bash
systemctl status marka-guardian
journalctl -u marka-guardian --since '10 minutes ago' --no-pager
docker logs --tail 50 marka-bridge-1
docker exec marka-mark-1 marka doctor
cat /var/lib/marka-guardian/status/status.json
```

Не запускай обычный `docker compose up` для сервиса `mark` поверх этой установки:
его стандартная конфигурация не содержит защищённых mounts. Также не запускай
отдельный `compose run mark login`: вход принадлежит единственному bridge.
Новый логин при необходимости выполняется оператором в том же bridge-каталоге.
Обновление bridge, guardian или зависимостей — отдельный выпуск оператора,
проверяемый до переключения. Сам Марк этих полномочий не получает.

При начальной установке останови прежний Telegram poller до запуска bridge,
передай ему сохранённый offset, проверь исходную базу и только затем запускай
бота без секретов. После первого возможного подтверждения сообщений bridge
нельзя возвращаться к старому прямому poller: уже принятые сообщения могут быть
только в новом журнале. Нужен совместимый с bridge резервный runtime.

## Что защита не обещает

Зелёные тесты не доказывают полезность на любой задаче. Произвольный Python
может подделать проверки внутри собственного процесса; поэтому это свидетельство
регрессий, дополненное внешними проверками хоста. Кандидат всё ещё может неверно
рассуждать или испортить свои рабочие файлы. `/rescue` восстанавливает базу,
но не обещает сохранить каждое промежуточное вычисление или файл.

Сбой диска или всего сервера требует внешней резервной копии. Компрометация
хоста не покрывается границей контейнера. Торговля, платежи, публикации и доступ
к новым аккаунтам этим механизмом не разрешаются. Для оценки полезности нужны
отдельные реальные задачи, отзывы владельца и сравнение с исходной версией.
