# Архив, память и поиск

SQLite хранит канонические эпизоды и знания. Проекции поиска можно построить
повторно: они не заменяют исходники и не дают записи статус подтверждённого факта.
Веса основной модели не меняются.

## Что сохраняется

По умолчанию `retention_days=0`: все записанные L0-эпизоды сохраняются бессрочно.
`Store.prune()` и `Store.prune(0)` ничего не удаляют. Положительное число дней —
явная политика хранения; она удаляет только старые эпизоды, которые не являются
источниками действующих кандидатов или принятых знаний. При обновлении старой
установки нужно проверить её сохранённый `retention_days`, а не только новый default.

Сохраняется текст, поступивший в Store, после удаления распознанных секретов.
Это не запись скрытого reasoning модели и не обещание сохранить все данные,
которые внешний сервис не вернул или приложение не записало. Текстовый эпизод
содержит до 40 000 символов, структурированное наблюдение инструмента —
до 250 000; импортёр делит длинные сообщения на части с устойчивыми ID.

Знание хранит тип, уровень, статус, автора, класс свидетельства и снимки источников
с SHA-256. Принятая запись с тем же ключом атомарно заменяет предыдущую.
`forgotten` и `superseded` исключены из обычного поиска; связанные с ними исходные
эпизоды также исключены из истории, поиска эпизодов и навигационных проекций.
Это подавление известных связей по ID, а не семантическое удаление всех возможных
пересказов из архива. Аудит и уже сделанные резервные копии физически не стираются.

## Точное чтение источника

Внутренние API возвращают точные фрагменты сохранённого текста:

| Метод | Результат |
| --- | --- |
| `get_event(id, offset=0, limit=4000)` | Страница эпизода, метаданные и происхождение импортированной записи |
| `get_memory(id, offset=0, limit=4000)` | Страница знания и метаданные снимков источников |
| `get_memory(id, source_id=event_id, offset=0, limit=4000)` | Страница неизменяемого снимка указанного источника |
| `memory_page(status='candidate', limit=10, before_id=None)` | Записи и `next_cursor` для следующей страницы |
| `list_memories(..., before_id=None)` | Совместимый список без контейнера пагинации |
| `history(session='main', limit=12, before_id=None)` | Более старые видимые эпизоды в хронологическом порядке |

Страница содержит `offset`, `total_chars`, `next_offset` и `content_hash`.
Смещения измеряются символами Python, не байтами. Хеш относится ко **всему**
сохранённому тексту, а не только к странице. Максимальная страница — 8000 символов.
Снимок источника остаётся доступен для аудита после явной очистки исходного эпизода.
Неактивные записи по умолчанию возвращают `None`; `include_inactive=True` предназначен
для отдельного просмотра аудита владельцем, а не для контекста агента.

Курсор — ID последней записи, а не номер страницы. Новые вставки между запросами
не сдвигают уже пройденную часть списка.

## Лексический поиск

Обязательный поиск работает без дополнительных Python-зависимостей и нейросетей:

1. Unicode NFKC, приведение регистра и `ё → е`.
2. Полнотекстовое совпадение по исходным словам и упрощённым русским формам.
3. Небольшой явный словарь технических вариантов: например, Telegram/телеграм/ТГ
   и Wildberries/WB/вайлдберриз. Словарь — соглашение поиска, не извлечённое знание.
4. Перекрывающиеся фрагменты до 1200 символов с исходными смещениями. Для длинного
   эпизода возвращается до 2000 символов около найденного места, а не всегда начало.
5. FTS5 BM25 отбирает до 600 фрагментов; затем совпадение слов, покрытие запроса,
   нормализованные формы и алиасы определяют порядок. Уровень памяти даёт небольшой
   дополнительный вес, поэтому точный L1-факт может оказаться выше общего L2-урока.

Обрезание русских окончаний — ограниченная эвристика. Это не полная лемматизация,
исправление опечаток или понимание синонимов. Релевантность не доказывает истинность.
Предложения модели попадают в обычный поиск знаний только после принятия;
явный `include_candidates=True` позволяет отдельно рассмотреть кандидатов.

`related_events` связывает соседние эпизоды задачи/сессии и буквальные упоминания.
`entity_links` показывает названия, идентификаторы и домены вместе с ID,
смещениями и хешами источников. Это навигационные подсказки: одинаковая строка
не доказывает тождество людей, проектов или фактов. Автоматического принятия знаний нет.

## Импорт длительного архива

`import_events(records, source)` атомарно принимает до 1000 записей за вызов.
Поля: `external_id` (или `id`), `role`, `content`, `created_at` (или `timestamp`),
необязательные `session` и `meta`. Время — ISO 8601 с часовым поясом или Unix seconds.
Возвращается число `imported` и `skipped`.

Ключ повторного импорта — пара `source + external_id`. Внутренний ID всегда новый;
старый внешний числовой ID не может заменить текущий источник памяти. Повтор той же
записи пропускается, конфликтующие содержание/роль/исходное время отклоняются.
ID, роль, исходное время, хеш и метаданные происхождения сохраняются отдельно;
явное удаление эпизода по retention не разрешает повторно импортировать его незаметно.

Импортированные сообщения получают `historical_unverified`. Старые ответы ассистента
не становятся фактами владельца. Исходные метаданные вложены в `origin_meta`, чтобы
исторический ключ `job` не мог притвориться текущим заданием. Личный JSONL и SQLite
остаются вне Git. Поиск извлекает относящиеся фрагменты; весь архив в промпт не передаётся.

## Миграции, резервные копии и размер

Миграция добавляет таблицы и индексы, сохраняя канонические ID и снимки.
SQL-триггеры помечают новые, изменённые и удалённые источники; поиск обновляет
производные фрагменты и упоминания в транзакции. Прямые SQL-вставки приложения
также учитываются. После большого импорта первый поиск строит накопившуюся проекцию.
Резервная копия использует SQLite backup API, а не копирование открытого WAL-файла.

Контрольная синтетическая проверка на Windows, 18 сентября 2026: 22 000 коротких
эпизодов, импорт 20,473 с; первый поиск вместе с построением проекций 17,160 с;
повторный запрос 0,381 с; согласованная копия 1,000 с и 78 295 040 байт.
После открытия копии сохранены все 22 000 записей. Это измерение искусственного
набора на машине разработки; объём и скорость реального архива могут отличаться.
Длинные тексты, FTS-индексы, снимки и векторы требуют дополнительного диска.

## Необязательный локальный семантический поиск

`semantic.py` добавляет локальные векторы и гибридное извлечение, сохраняя SQLite
источником истины. Отдельный производный индекс проверяет текущий статус и полный
хеш источника перед выдачей результата. Модель скачивается явно; локальное кодирование
текста не отправляет его во внешний embedding API. Лексический поиск остаётся
доступным без модели и дополнительных пакетов.

Выбранная модель — [multilingual MiniLM L12](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2/tree/e8f8c211226b894fcb81acc59f3b34ba3efd5f42),
Apache-2.0, 384 координаты и контекст до 128 токенов. Закреплённый ONNX INT8 AVX2
весит 118 453 870 байт, tokenizer — 9 081 518 байт. Для CPU-пути нужны ONNX Runtime,
tokenizers и NumPy; PyTorch и sentence-transformers в runtime не требуются.
Сборка использует mean pooling с attention mask и нормализацию вектора согласно
[официальной карточке модели](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2).

Исследованная альтернатива — [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/tree/614241f622f53c4eeff9890bdc4f31cfecc418b3),
MIT: официальный INT8 ONNX 118 346 824 байт и tokenizer 17 082 730 байт; опубликованный
вариант ориентирован на AVX512 VNNI. У обеих моделей FP32 ONNX около 470 MB, что почти
исчерпывает лимит 500 MB ещё до установки библиотек. Поэтому для малого сервера
рассматривается только закреплённый INT8-путь с измерением на целевом CPU.

Проверенный путь добавляет локально преобразованный ORT-файл для mmap: всего около
433 MB дополнительного установленного диска с библиотеками, без пользовательских
индексов. Полный синтетический прогон с 2004 источниками прошёл в отдельном контейнере
512 MiB / 1 CPU, но процесс после запросов занимал около 424 MB RSS; совместная
работа с агентом требует дополнительного запаса. Предел RAM **не следует** из размера
весов. Параметры, исходные неудачные прогоны и границы выводов — в [SEMANTIC.md](SEMANTIC.md).
Квантизация может изменить качество;
[документация ONNX Runtime](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
рекомендует сравнивать результаты после преобразования. Точные проверки установленной
сборки фиксируются в VALIDATION, а не выводятся из названия модели.
