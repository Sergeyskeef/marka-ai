# Длительные задачи и проверка результата

Марк хранит план, наблюдения, артефакты и бюджет задачи в SQLite. Конец рабочего
отрезка не означает конец задачи: worker может вернуть её в очередь без нового
итогового сообщения, сохранив общий бюджет. Это позволяет продолжать работу
после первых 12 решений модели.

## Контракт очереди

`claim()` возвращает новый `lease` для каждой попытки. Worker передаёт этот lease
в `checkpoint`, `reserve_call`, `record_step`, `record_artifact`, `save_plan`,
`requeue` и `finish`. После отмены, восстановления или новой попытки старый lease
не может изменить задачу. Параметр `lease=None` в старых `checkpoint`/`finish`
оставлен только для совместимости; новый runtime обязан передавать lease.

`configure_task(id, max_steps=48, max_model_calls=64, max_seconds=900)` задаёт
лимиты один раз. Повторный вызов не пополняет бюджет. Не настроенные старые
задачи сохраняют совместимость без лимитов очереди. Каждое решение модели
предварительно списывается через `reserve_call(id, lease)`; консультация через
`step=False` расходует вызов модели, но не основной шаг. Списание атомарно и
сохраняется, даже если процесс прервётся во время запроса.

Отсчёт времени начинается при первом `claim`, а не при постановке будущей задачи
в очередь. После запуска действует абсолютный deadline: паузы, рестарты и ожидание
следующего отрезка входят в него. `/resume` не сбрасывает ни deadline, ни счётчики.
Для осознанного продолжения сверх лимита существует отдельный `extend_budget`
с `extra_steps`, `extra_model_calls`, `extra_seconds`. Этот API предназначен
только для явно авторизованной команды владельца и сам задачу не запускает.
Продление истёкшего времени отсчитывается от момента продления.
Для команды Telegram передаётся уникальный `source`, например
`telegram:extend:123`: квитанция продления записывается одной транзакцией с
лимитами, поэтому повтор update после аварии не добавит бюджет второй раз.

`requeue(id, lease, trace, summary, delay=0)` допустим только между действиями;
неоднозначный `inflight` инструмент не переигрывается автоматически. `finish`
по-прежнему атомарно сохраняет итог, ставит сообщение в outbox и создаёт следующий
запуск конечного расписания. Дубликат либо поздний итог ничего не меняет.

План — до 12 плоских записей `{title, status, evidence}`. Статус плана отражает
утверждение о ходе работы и отдельно проверяется наблюдениями. `record_step`
сохраняет неизменяемый исход по номеру шага и ссылку `event_id`; повторный номер
не перезаписывает доказательство. Крупные поля становятся явно сокращёнными
представлениями с SHA-256. `progress` возвращает последние 20 шагов, последние
100 артефактов, план, бюджет и итог проверки. `evidence_trace` восстанавливает все
сохранённые шаги для проверки независимо от сокращения контекста модели.
При обновлении старой задачи он объединяет сохранившиеся пары из checkpoint
с новыми `task_steps`, убирая дубли по `event_id`. Канонический текст события
используется только при совпадении role, session, job и tool. Полный современный
шаг остаётся неизменяемым; сокращённый шаг восстанавливается из события лишь
при совпадении SHA-256 нормализованного очищенного JSON. Чужое событие не может
стать источником, а удаление старых событий не стирает сохранившийся checkpoint.

## Что подтверждает verifier

`verify_completion(trace, workspace=..., model_outcome="completed",
expected_artifacts=...)` принимает журнал, сформированный runtime. Модель не
передаёт ему собственный список доказательств.

- `observed`: есть подтверждённое наблюдение и нет оставшегося противоречия.
- `unverified`: недостаточно наблюдений; обычный разговор может иметь этот статус.
- `contradicted`: наблюдения противоречат успешному завершению — например, команда
  завершилась с ошибкой, runner сообщил timeout/ошибку артефактов или созданный
  файл исчез/изменился относительно квитанции.

Verifier проверяет фактические байты файлов, размер и SHA-256. Успешный повтор
того же инструмента и цели закрывает предыдущую ошибку. Успех другой команды
не скрывает ошибку первой. Для `code.run` цель — весь argv; исправление файла с
повтором прежнего argv считается повтором того же действия. Итог модели остаётся
отдельным полем `model_outcome`. Очередь отправки файла — ещё не подтверждение
доставки Telegram; мнение консультации — не независимая проверка.

Отдельный случай — `error_kind="validation_rejected"`, который runtime ставит
только для `ToolInputError`: запрос отклонён до выполнения действия. Например,
небезопасный путь `../report.txt` можно исправить на `reports/report.txt`.
Такой отказ остаётся нерешённым до успешного вызова того же инструмента, но
исправленная цель может отличаться. Обычный `ValueError` не означает отсутствие
эффектов и не получает эту маркировку автоматически. Отказ валидации не стирает
предыдущую ошибку исполнения, timeout или проблему созданного файла.

`skill.run` проверяется как `code.run`: необходимы exit code 0, отсутствие
timeout/ошибки артефактов и действительные файловые квитанции. Его цель включает
имя навыка, параметры и пути входных данных; успешный запуск с другими
параметрами не скрывает предыдущую ошибку. `workspace.replace` проверяет
новую ревизию файла по тем же правилам, что и `workspace.write`.

Наличие успешного наблюдения не доказывает выполнение всех смысловых требований
пользователя. Например, exit code 0 подтверждает исход конкретного запуска, но
не правильность программы во всех случаях. Успешные эксперименты с собственным
кодом по-прежнему создают кандидат и отчёт без автоматической установки.

## Независимый набор сценариев

```sh
python -m marka.evaluation --output acceptance.json
```

Команда выполняет 16 детерминированных сценариев в новых временных SQLite и
workspace: память после перезапуска; непринятый кандидат; исправление и забывание
факта; задача длиннее 12 шагов; отмена/продолжение; исчерпание бюджета; прерывание
инструмента; создание UTF-8 файла; изменение/исчезновение артефакта; исправление
ошибки программы; нерелевантный успешный запуск; ошибка сбора артефактов;
неподтверждённая доставка; голословное заявление модели о завершении.

Этот набор запускается отдельно от discovery unit tests и от тестов, предложенных
моделью для `self.experiment`. Он не вызывает модель, Telegram или сеть, не
исполняет произвольный код на хосте и не читает рабочее состояние владельца.
Сценарии ошибок программ здесь подают фиксированные квитанции runner: реальная
контейнерная изоляция отдельно проверяется `scripts/container_smoke.py`.

Это публичные фиксированные acceptance fixtures, а не тайный held-out benchmark.
Они измеряют поведение runtime и целостность доказательств. Отдельный live benchmark
модели может оценивать выбор действий, но должен иметь собственную квоту, явную
авторизацию и отдельный отчёт; прохождение этих 16 сценариев не означает рост
интеллекта модели. Python `-O` запрещён для этого набора, чтобы проверки нельзя
было случайно отключить.
