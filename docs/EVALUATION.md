# Длительные задачи и проверка результата

Марк хранит план, наблюдения, артефакты и бюджет задачи в SQLite. Конец рабочего
отрезка не означает конец задачи: worker может вернуть её в очередь без нового
итогового сообщения, сохранив общий бюджет. Это позволяет продолжать работу
после первых 12 решений модели.

## Контракт очереди

`claim()` возвращает новый `lease` для каждой попытки. Worker передаёт этот lease
в `checkpoint`, `reserve_call`, `record_step`, `record_artifact`, `save_plan`,
`requeue` и `finish`. После отмены, восстановления или новой попытки старый lease
не может изменить задачу. Параметр `lease=None` в старых `checkpoint`/`finish`
оставлен только для совместимости; новый runtime обязан передавать lease.

`configure_task(id, max_steps=48, max_model_calls=64, max_seconds=900)` задаёт
лимиты один раз. Повторный вызов не пополняет бюджет. Не настроенные старые
задачи сохраняют совместимость без лимитов очереди. Каждое решение модели
предварительно списывается через `reserve_call(id, lease)`; консультация через
`step=False` расходует вызов модели, но не основной шаг. Списание атомарно и
сохраняется, даже если процесс прервётся во время запроса.

Отсчёт времени начинается при первом `claim`, а не при постановке будущей задачи
в очередь. После запуска действует абсолютный deadline: паузы, рестарты и ожидание
следующего отрезка входят в него. `/resume` не сбрасывает ни deadline, ни счётчики.
Для осознанного продолжения сверх лимита существует отдельный `extend_budget`
с `extra_steps`, `extra_model_calls`, `extra_seconds`. Этот API предназначен
только для явно авторизованной команды владельца и сам задачу не запускает.
Продление истёкшего времени отсчитывается от момента продления.
Для команды Telegram передаётся уникальный `source`, например
`telegram:extend:123`: квитанция продления записывается одной транзакцией с
лимитами, поэтому повтор update после аварии не добавит бюджет второй раз.

`requeue(id, lease, trace, summary, delay=0)` допустим только между действиями;
неоднозначный `inflight` инструмент не переигрывается автоматически. `finish`
по-прежнему атомарно сохраняет итог, ставит сообщение в outbox и создаёт следующий
запуск конечного расписания. Дубликат либо поздний итог ничего не меняет.

План — до 12 плоских записей `{title, status, evidence}`. Статус плана отражает
утверждение о ходе работы и отдельно проверяется наблюдениями. `record_step`
сохраняет неизменяемый исход по номеру шага и ссылку `event_id`; повторный номер
не перезаписывает доказательство. Крупные поля становятся явно сокращёнными
представлениями с SHA-256. `progress` возвращает последние 20 шагов, последние
100 артефактов, план, бюджет и итог проверки. `evidence_trace` восстанавливает все
сохранённые шаги для проверки независимо от сокращения контекста модели.
При обновлении старой задачи он объединяет сохранившиеся пары из checkpoint
с новыми `task_steps`, убирая дубли по `event_id`. Канонический текст события
используется только при совпадении role, session, job и tool. Полный современный
шаг остаётся неизменяемым; сокращённый шаг восстанавливается из события лишь
при совпадении SHA-256 нормализованного очищенного JSON. Чужое событие не может
стать источником, а удаление старых событий не стирает сохранившийся checkpoint.

## Дата и календарные поручения

Каждое решение получает `current_time` с текущим временем UTC, местным временем,
настроенным `timezone` и днём недели. Настройка по умолчанию — `UTC`; фиксированные
смещения `UTC+03:00` работают без дополнительных пакетов, IANA-зоны используют
установленную системную базу. `MARKA_TIMEZONE` может переопределить настройку
процесса; `setup --timezone UTC+03:00` сохраняет её.

`task.schedule` принимает ровно один вариант времени: целое `delay_seconds` или
`due_at` в RFC3339 с секундами и явным UTC-смещением. Даты без смещения, неизвестное
`-00:00`, прошлые моменты и запуск позже 366 дней отвергаются до создания задания.
Дата хранится как UTC timestamp и переживает перезапуск. Квитанция показывает
действительно сохранённый момент, в том числе при повторе того же вызова.
`/tasks` показывает время ожидающего расписания в настроенном поясе.

Повтор остаётся интервалом в секундах, минимум 300, максимум 366 дней и не более
100 запусков. Следующий интервал отсчитывается от завершения предыдущего запуска;
это не правило «каждый день ровно в девять». Он не сохраняет местный час при смене летнего времени. Очередь
начинает просроченное поручение после восстановления сервиса; точность доставки
зависит от доступности worker, модели и Telegram, это не гарантированный таймер.

Ключи отправки файлов и создания расписаний используют сохранённый номер решения,
а не длину сжатого контекста. Поэтому новый шаг после продолжения длинной задачи
не может случайно принять квитанцию прежнего действия. Отдельный префикс версии
защищает незавершённые задачи от пересечения со старыми ключами.

## Что подтверждает verifier

`verify_completion(trace, workspace=..., model_outcome="completed",
expected_artifacts=..., criteria_contract=...)` принимает журнал, сформированный runtime. Модель не
передаёт ему собственный список доказательств.

- `observed`: есть подтверждённое наблюдение и нет оставшегося противоречия.
- `unverified`: недостаточно наблюдений; обычный разговор может иметь этот статус.
- `contradicted`: наблюдения противоречат успешному завершению — например, команда
  завершилась с ошибкой, runner сообщил timeout/ошибку артефактов или созданный
  файл исчез/изменился относительно квитанции.

Verifier проверяет фактические байты файлов, размер и SHA-256. Успешный повтор
того же инструмента и цели закрывает предыдущую ошибку. Успех другой команды
не скрывает ошибку первой. Для `code.run` цель — весь argv; исправление файла с
повтором прежнего argv считается повтором того же действия. Итог модели остаётся
отдельным полем `model_outcome`. Очередь отправки файла — ещё не подтверждение
доставки Telegram; мнение консультации — не независимая проверка.

Отдельный случай — `error_kind="validation_rejected"`, который runtime ставит
только для `ToolInputError`: запрос отклонён до выполнения действия. Например,
небезопасный путь `../report.txt` можно исправить на `reports/report.txt`.
Такой отказ остаётся нерешённым до успешного вызова того же инструмента, но
исправленная цель может отличаться. Обычный `ValueError` не означает отсутствие
эффектов и не получает эту маркировку автоматически. Отказ валидации не стирает
предыдущую ошибку исполнения, timeout или проблему созданного файла.

`skill.run` проверяется как `code.run`: необходимы exit code 0, отсутствие
timeout/ошибки артефактов и действительные файловые квитанции. Его цель включает
имя навыка, параметры и пути входных данных; успешный запуск с другими
параметрами не скрывает предыдущую ошибку. `workspace.replace` проверяет
новую ревизию файла по тем же правилам, что и `workspace.write`.

Наличие успешного наблюдения не доказывает выполнение всех смысловых требований
пользователя. Например, exit code 0 подтверждает исход конкретного запуска, но
не правильность программы во всех случаях. Успешные эксперименты с собственным
кодом создают кандидат и отчёт; запрос его установки отдельно проверяет guardian.

## Критерии конкретной задачи

`task.criteria` фиксирует проверяемый результат до действий, меняющих файлы или
внешнее состояние. Предварительное чтение, поиск и планирование разрешены.
Критерии хранятся в существующей таблице `meta` с привязкой к номеру задачи,
исходному `source`, SHA-256 её запроса и текущему рабочему lease. Новых таблиц или
миграций для этого нет. Продолжение задачи после перезапуска использует те же
критерии. Точный повтор объявления идемпотентен; заменить, удалить или ослабить
условия модель не может. Повреждённая запись блокирует проверку, а не становится
отсутствующим условием.

Критерии предлагает модель: в записи явно указаны `proposer="model"` и
`owner_accepted=false`. Это не согласование со стороны владельца и не доказательство
того, что модель правильно поняла все требования. Проверяется объявленный
контракт; качество самого выбора условий всё ещё требует отдельных оценок.

Поддержаны четыре вида условий:

| `kind` | Условие | Основание |
| --- | --- | --- |
| `artifact` | Файл по заданному пути, границы размера, необязательный ожидаемый SHA-256 | Квитанция текущей задачи и фактические байты |
| `text_contains` | Все перечисленные строки присутствуют в UTF-8 файле | Буквальное сравнение, без регулярных выражений или модели |
| `json_matches` | Значения по ограниченным JSON Pointer совпадают с ожидаемыми | Разбор JSON, точное сравнение типов и значений; `true` не равно `1` |
| `command_succeeded` | Указанный argv действительно завершился успешно | Наблюдение `code.run`, exit code 0, отсутствие ошибки/timeout, argv и manifest входов |

Пример аргументов инструмента:

```json
{
  "criteria": [
    {"id": "sections", "kind": "text_contains", "path": "report.md", "contains": ["Итог", "Проверка"]},
    {"id": "total", "kind": "json_matches", "path": "summary.json", "assertions": [{"pointer": "/total", "equals": 42}]},
    {"id": "tests", "kind": "command_succeeded", "argv": ["python", "verify_report.py"]}
  ]
}
```

На задачу допустимо 1–12 условий. Проверка содержимого читает максимум 1 MiB на
файл; проверка файловой квитанции ограничена 20 MiB. В текстовом условии допустимо
до 16 буквальных строк; JSON-условие содержит до 16 проверок, указатель — до 12
компонентов. Дубли ключей JSON, нечисловые `NaN`/`Infinity`, небезопасные пути и
переданный пользователем код проверки отвергаются. Проверяющий код не исполняет
объявленный argv и не обращается к сети: разрешены только квитанции известных
команд из изолированного runner.

Для проверки уже существующего файла подходит квитанция `workspace.read` этой
задачи с SHA-256. Простого наличия файла в общем workspace недостаточно. Для
созданного файла нужны квитанция записи/runner и совпадение текущих байтов. После
успешного запуска проверяется, что его входные `.py`, `.js`, `.mjs`, `.cjs` и `.sh`
файлы не изменились. Изменение кода после теста требует нового наблюдаемого запуска.
Успех другой команды не закрывает провал указанного argv.

Вложенный результат `acceptance` различает:

- `missing`: действие ещё не подтверждено или не хватает его квитанции;
- `failed`: проверяемое условие нарушено либо контракт повреждён;
- `pass`: все объявленные условия подтверждены.

Непройденный объявленный критерий делает общий результат `contradicted`, поэтому
runtime не должен принимать `outcome="completed"`. При этом модель может честно
завершить попытку как `blocked`. Пройденные критерии не скрывают другие ошибки
старого verifier. Обычный разговор без объявленных критериев остаётся допустимым.

Внутренние API: `freeze_criteria(queue, job_id, lease, criteria)`,
`get_criteria(queue, job_id)` и `evaluate_criteria(contract, trace,
workspace=..., expected_artifacts=...)`. `None` от `get_criteria` означает
отсутствие объявления; запись с `invalid=true` означает повреждение и должна
передаваться verifier как блокирующий контракт.

## Независимый набор сценариев

```sh
python -m marka.evaluation --output acceptance.json
```

Команда выполняет 16 детерминированных сценариев в новых временных SQLite и
workspace: память после перезапуска; непринятый кандидат; исправление и забывание
факта; задача длиннее 12 шагов; отмена/продолжение; исчерпание бюджета; прерывание
инструмента; создание UTF-8 файла; изменение/исчезновение артефакта; исправление
ошибки программы; нерелевантный успешный запуск; ошибка сбора артефактов;
неподтверждённая доставка; голословное заявление модели о завершении.

Этот набор запускается отдельно от discovery unit tests и от тестов, предложенных
моделью для `self.experiment`. Он не вызывает модель, Telegram или сеть, не
исполняет произвольный код на хосте и не читает рабочее состояние владельца.
Сценарии ошибок программ здесь подают фиксированные квитанции runner: реальная
контейнерная изоляция отдельно проверяется `scripts/container_smoke.py`.

Это публичные фиксированные acceptance fixtures, а не тайный held-out benchmark.
Они измеряют поведение runtime и целостность доказательств. Отдельный live benchmark
модели может оценивать выбор действий, но должен иметь собственную квоту, явную
авторизацию и отдельный отчёт; прохождение этих 16 сценариев не означает рост
интеллекта модели. Python `-O` запрещён для этого набора, чтобы проверки нельзя
было случайно отключить.

## Воспроизводимые проверки полезного результата

```sh
python -m marka.evaluation --suite usefulness --output usefulness.json
python -m marka.evaluation --suite cases --output frozen-cases.json
```

Первый режим запускает семь независимых синтетических сценариев: создание отчёта
с нужными разделами и числами; исправление команды с последующей проверкой кода;
невозможность ослабить условие после неудачи; нерелевантный успешный запуск;
голословное итоговое сообщение; проверка существующего файла; обычный разговор.
Файлы и SQLite в этих сценариях настоящие временные, а квитанции runner заданы
тестовым сценарием. Модель, Telegram и сеть не вызываются; команды не исполняются.
Отчёт явно хранит `fixture_kind="public_synthetic"`, происхождение наблюдений и
нулевые счётчики модели, сети и запуска команд.

Второй режим экспортирует два заранее заданных задания для отдельной проверки
модели: структурированный отчёт и исправление `calculator.py` при неизменном
`verify_report.py`. Экспорт включает запросы, начальные файлы, ожидаемые критерии
и SHA-256 набора. Экспорт сам по себе не запускает модель. Для реального прогона
нужно сначала сохранить этот набор, затем создать отдельные временные задачи и
workspace, собрать их фактические журналы/артефакты и проверить именно исходные
критерии. Нельзя заменять их облегченными условиями, предложенными моделью во время
попытки, или принимать придуманные квитанции из её ответа.

Эти публичные задания не являются скрытым benchmark. Прохождение семи сценариев
подтверждает работу контроля результата и обработки ошибок. Утверждение, что
модель стала полезнее, требует отдельного сопоставимого прогона исходной и новой
версий на замороженных заданиях; этот пакет такого сравнения не заявляет.
