# Mark - Автономная система с самоосознанием

## История миграции и синхронизации с сервером (2025-06)

В июне 2025 года проект был полностью перенесён с боевого сервера на GitHub. Теперь репозиторий содержит **актуальную, рабочую версию** кода, зависимостей и инфраструктуры, используемых в продакшене.

### Как происходила миграция

1. **Инициализация git на сервере**
   - В папке с рабочим проектом был выполнен `git init`.
   - Добавлен remote на GitHub:
     ```
     git remote add origin git@github.com:Sergeyskeef/marka-ai.git
     ```

2. **Настройка SSH-доступа**
   - На сервере был сгенерирован SSH-ключ (`ssh-keygen -t ed25519 -C "deploy@marka"`).
   - Публичный ключ добавлен в GitHub (Settings → SSH and GPG keys).
   - Проверено соединение:
     ```
     ssh -T git@github.com
     ```
     Должно появиться сообщение об успешной аутентификации.

3. **Перенос содержимого на GitHub**
   - Создана ветка main:
     ```
     git checkout -b main
     ```
   - Все файлы и папки добавлены в индекс:
     ```
     git add .
     git commit -m "Сделать серверную версию основной"
     ```
   - Выполнен принудительный push (force push), чтобы полностью заменить содержимое ветки main на GitHub:
     ```
     git push --force origin main
     ```
   - Теперь на GitHub находится точная копия серверной версии проекта.

4. **Особенности структуры**
   - В проекте есть вложенные git-репозитории (например, `cursor_memory`, `langchain_api`). Git предупредил об этом, но если это не отдельные проекты, их можно оставить как есть. Если это ошибка — используйте:
     ```
     git rm --cached cursor_memory
     git rm --cached langchain_api
     ```

5. **Проверка**
   - После push все файлы, папки, зависимости и скрипты на GitHub полностью совпадают с сервером.
   - Теперь любые изменения на сервере можно пушить на GitHub, и наоборот.

### Зачем это сделано

- **Контроль версий:** теперь история изменений хранится централизованно.
- **Безопасность:** можно быстро восстановить проект или развернуть его на новом сервере.
- **Автоматизация:** включён CI/CD — любые коммиты автоматически запускают тесты, сборку и деплой.
- **Командная работа:** все члены команды могут работать с одной и той же версией кода.

### Важно для будущих изменений

- **Работайте только через git:** любые изменения фиксируйте коммитами и пушьте на GitHub.
- **CI/CD:** после каждого push автоматически запускается пайплайн (см. раздел "CI/CD Pipeline" ниже).
- **SSH-ключи:** для доступа к репозиторию с сервера используйте только SSH-ключи, не пароли.

## Система предложений и саморазвития

### Генерация и история предложений
- Марк автоматически формирует предложения по улучшениям на основе самоанализа и истории выполнения задач.
- Все предложения хранятся централизованно, доступны для анализа и управления как системой, так и пользователем.
- История предложений и их статусов сохраняется (новое, принято, отклонено, реализовано).

### Команды Telegram-бота
- `/self_improve` — сгенерировать и показать свежие предложения по улучшениям
- `/improve_history` — показать историю всех предложений и их статусов
- `/accept_improvement <id>` — принять предложение (меняет статус и автоматически создаёт задачу)
- `/reject_improvement <id>` — отклонить предложение

### Автоматизация
- При принятии предложения автоматически создаётся задача через TaskExecutor, id задачи сохраняется в history предложения.
- Все действия доступны для анализа и дальнейшей автоматизации (например, повторное предложение, если задача не реализована).

### Пример использования
1. Вызвать `/self_improve` — получить свежие предложения.
2. Принять предложение `/accept_improvement <id>` — автоматически создастся задача.
3. Посмотреть историю `/improve_history` — увидеть все предложения, их статусы и связанные задачи.

### Интеграция с TaskExecutor
- Все предложения, принятые к реализации, становятся задачами с категорией CUSTOM и приоритетом MEDIUM.
- История связана: предложение знает id задачи, задача — причину создания.

## Система рефлексии и самоанализа

### ReflectionAnalyzer

`ReflectionAnalyzer` - это компонент, который анализирует выполненные действия и генерирует инсайты на основе их анализа. Он является частью расширенной системы рефлексии и самоанализа.

#### Основные возможности:

- Отслеживание истории выполненных действий
- Анализ последовательности действий
- Оценка эффективности действий
- Генерация инсайтов и рекомендаций

#### Пример использования:

```python
from langchain_api.core.reflection.reflection_analyzer import ReflectionAnalyzer

# Создание анализатора
analyzer = ReflectionAnalyzer()

# Добавление действий
analyzer.add_action({
    'type': 'code_analysis',
    'target': 'test_file.py',
    'result': 'success',
    'duration': 1.5
})

# Анализ действий и получение инсайтов
insights = analyzer.analyze_actions()
```

#### Структура действий:

Каждое действие должно содержать следующие поля:
- `type`: тип действия (например, 'code_analysis', 'test_execution')
- `target`: цель действия (например, имя файла)
- `result`: результат выполнения
- `duration`: продолжительность выполнения (опционально)

#### Структура инсайтов:

Инсайты содержат следующую информацию:
- `type`: тип инсайта ('sequence_analysis' или 'efficiency_analysis')
- `action_type`: тип действия, к которому относится инсайт
- `insight`: текстовое описание инсайта
- `timestamp`: время генерации инсайта

## CI/CD Pipeline

Проект использует GitHub Actions для автоматизации сборки, тестирования и деплоя. Pipeline включает следующие этапы:

1. **Тестирование**
   - Запуск unit-тестов с помощью pytest
   - Проверка покрытия кода тестами
   - Линтинг кода с помощью ruff

2. **Сборка**
   - Сборка Docker-образа
   - Публикация образа в Docker Hub
   - Кэширование слоев для ускорения сборки

3. **Деплой**
   - Автоматический деплой на сервер при успешной сборке
   - Проверка здоровья приложения
   - Откат к предыдущей версии при ошибках

### Локальная разработка

Для локальной разработки используйте docker-compose:

```bash
# Сборка и запуск контейнеров
docker compose up --build

# Запуск тестов
docker compose exec app pytest

# Проверка линтером
docker compose exec app ruff check .
```

### Переменные окружения

Создайте файл `.env` в корне проекта:

```env
OPENAI_API_KEY=your_api_key
ENVIRONMENT=development
```

### Мониторинг

- Проверка здоровья: `http://localhost:8000/health`
- Логи: `docker compose logs -f app`

## Настройка CI/CD

### 1. Создание аккаунта на Docker Hub

1. Зарегистрируйтесь на [Docker Hub](https://hub.docker.com)
2. Создайте новый репозиторий `marka`
3. Создайте access token в настройках аккаунта

### 2. Настройка GitHub Secrets

Добавьте следующие секреты в настройках репозитория GitHub:

- `DOCKERHUB_USERNAME` - ваше имя пользователя на Docker Hub
- `DOCKERHUB_TOKEN` - ваш access token Docker Hub
- `SERVER_HOST` - IP-адрес или домен вашего сервера
- `SERVER_USERNAME` - имя пользователя для SSH
- `SERVER_SSH_KEY` - приватный SSH-ключ для доступа к серверу

### 3. Настройка сервера

1. Установите Docker и Docker Compose:
```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo apt-get install docker-compose-plugin
```

2. Создайте пользователя для деплоя:
```bash
sudo useradd -m -s /bin/bash deploy
sudo usermod -aG docker deploy
```

3. Настройте SSH-ключи:
```bash
sudo mkdir -p /home/deploy/.ssh
sudo touch /home/deploy/.ssh/authorized_keys
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh
sudo chmod 600 /home/deploy/.ssh/authorized_keys
```

4. Скопируйте публичный ключ в authorized_keys:
```bash
echo "YOUR_PUBLIC_KEY" | sudo tee -a /home/deploy/.ssh/authorized_keys
```

### 4. Проверка деплоя

1. Сделайте push в ветку main:
```bash
git add .
git commit -m "test: add CI/CD configuration"
git push origin main
```

2. Проверьте статус деплоя в GitHub Actions
3. Проверьте логи деплоя на сервере:
```bash
tail -f /home/sergey/marka/logs/deploy.log
```

4. Проверьте здоровье приложения:
```bash
curl http://localhost:8000/health
```
